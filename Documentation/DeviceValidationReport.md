# Device validation report format

Every release candidate needs one report generated by
`Scripts/run-device-validation.sh` for each tested physical device.

The report must contain:

- device model identifier;
- exact iOS build and Xcode version;
- package test-action result;
- route and model state;
- manual lifecycle scenarios from `DeviceMatrix.md`;
- observed latency, memory, heat, failures, and recovery behavior;
- linked issue IDs for every failure;
- a privacy check confirming that no speech content or raw device identifier was retained.

Do not attach recordings, transcript text, TTS text, credentials, or crash
attachments containing user speech. Use synthetic test phrases when a note
needs an example.

`Scripts/run-device-validation.sh` creates a scaffold after the automated
physical-device package test. It intentionally leaves manual rows `_pending_`;
it is a collection step, not the release acceptance gate. After completing the
matrix, run:

The collector requires a connected physical device identifier and uses
`devicectl` for the exact model, model identifier, OS version, and OS build. It
retains the `.xcresult` bundle and xcodebuild log beside the report. To append
the report atomically to a cross-device manifest, pass a third and fourth
argument:

```sh
Scripts/run-device-validation.sh \
  <device-udid> \
  Documentation/device-reports/<utc-device-report>.md \
  --manifest Documentation/device-reports-manifest.json
```

The collector exits non-zero if the device is missing, metadata is incomplete,
the test action fails, artifacts cannot be retained, or the manifest cannot be
updated. A successful automated package test still leaves the manual matrix
pending and therefore is not a release pass.

```sh
python3 Scripts/validate-device-report.py \
  Documentation/device-reports/<utc-device-report>.md \
  --require-complete \
  --require-release
```

The validator requires physical-device metadata, a retained result bundle, a
passed package test, a completed privacy review, and `pass` or `fail` for every
scenario row. Release mode additionally requires the retained xcodebuild log
to contain `TEST SUCCEEDED`, and rejects failed scenarios unless each one has
an explicit waiver in this table. With both `--require-complete` and
`--require-release`, failures may therefore be waived, while `_pending_` and
`unknown` results remain invalid:
When the retained bundle is a native Xcode result bundle, the validator also
asks `xcrun xcresulttool` to read its test summary.

## Cross-report manifest validation

The normal command above remains the single-report acceptance check. To check
several reports together, create a UTF-8 JSON manifest with a `reports` array.
Paths are resolved relative to the manifest file when they are not absolute;
the report metadata is authoritative, so the manifest cannot override a
device or OS value.

```json
{
  "reports": [
    "device-reports/iphone-17-pro.md",
    "device-reports/ipad-pro.md"
  ]
}
```

Run the optional cross-report check with the same acceptance flags when
appropriate:

```sh
python3 Scripts/validate-device-report.py \
  --manifest Documentation/device-reports-manifest.json \
  --require-complete \
  --require-release
```

Manifest mode first applies all single-report rules to every listed report.
It then treats each scenario as a normalized row keyed by:

`device model identifier / iOS build / route / scenario ID`

For `route.*` scenarios, `route` is the complete scenario ID; other scenarios
use `none`. Repeated keys are rejected as duplicate rows. If repeated keys
have different results, they are rejected as contradictory rows. Reports with
the same device model identifier and iOS build must also agree on device model,
displayed iOS version, Toolchain, and SDK. Duplicate manifest paths, malformed
manifests, and empty report lists are rejected. The single-report invocation
does not read or require a manifest.

```markdown
## Release waivers

| Scenario ID | Waiver / issue | Owner | Approval / expiry |
|---|---|---|---|
| interruption.phone-call | issue-123 | maintainer | approved 2026-08-01 |
```

The required scenario set includes media-services reset, premium-voice
availability, active `close()` cleanup, process relaunch recovery, and
hardware-capability reporting in addition to the route/model/interruption
matrix. A waiver is an exception record, not a passing result; it must identify
the issue, owner, and approval/expiry information and should be reviewed before
publication.
